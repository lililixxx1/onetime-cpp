# 性能专项优化方案（2026-09-10）

目标：精简热路径、提升并发吞吐，并把 EUI-NEO 的按需重绘/async 模型用对。
所有改动不触碰 server.cpp 头部列出的 12 条安全不变量，行为对外保持等价。

## 现状问题清单（按收益排序）

### P1 服务端连接串行（server.cpp accept 循环）

`runServer` 的 accept 循环里 `handleConnection(sv, client)` 是**同步调用**：
一个慢客户端（如建立连接后挂着不发的探测连接，最长吃满 30s 连接预算）
会阻塞所有后续连接——包括 GUI 自己的 HTTP 调用。测试里的
"8 线程抢单"目前实际是串行执行的，并发语义没有真正兑现。

**方案**：accept 后起分离线程执行 `handleConnection`，配合原子计数上限
（128 个活跃连接，超限立即关闭 socket）防线程耗尽。`Server sv` 在 runServer
栈上且 accept 循环永不返回，跨线程引用安全；Store/vault/log 各有互斥锁，
`cfg` 监听后只读，无新增数据竞争。

实现要点（plan-code-reviewer 审核补入）：
- 计数递减必须在包装层统一完成（handleConnection 有大量早退分支，散置递减会泄漏）。
- listen backlog 16 → 128，与并发上限配套。
- 超限连接先回最小 503（含安全头）再关闭，客户端拿到可读错误而非空响应。
- 既有风险说明：进程退出期 CRT 静态析构（g_logSink）可能与分离线程的
  logEvent 并发，现状已存在，P1 将线程数 1→N 放大撞面；不破坏"密文随进程
  清空"不变量，接受不改。

### P2 richParagraph 每 compose 全量 O(n²) 文本测量（main.cpp）

`richParagraph`（票据说明两色混排）每次 compose 都重新分词 + 逐 token
调 `core::TextPrimitive::measureTextWidth(lineText + tok.s)`。每次测量
从行首起量整行，~150 个 token 的一段说明 ≈ 上万次字形测量。而 compose
在票据显示期间的高频触发源：密钥框每个键入字符、复制反馈 1.6s /
toast 3s 的 timer 驱动帧、按钮 hover。这是 UI 层最大的重复 CPU 开销。

**方案**：按调用点缓存断行结果——输入（segments 文本+颜色、w、fontSize、
lineHeight）完全相等则直接复用上次的行数组，跳过分词与全部测量。
文本只在生成票据时变化一次，宽度只在窗口 resize 时变化，命中率接近 100%。
这是补 EUI-NEO 没有内置的富文本排版缓存（框架文本一段一色）。
缓存键核实（审核确认）：uiScale/fonts 均为启动期常量且 compose 期按逻辑单位
测量，主题色已在键内；键补 fontFamily/fontWeight（当前恒为默认值，零成本保险，
对齐框架自家 TextSizeCache 的键构成）；缓存按 id 分槽（现仅一个调用点，
分槽避免未来第二处调用互踢）。core::Color 无 operator==，判等自定义字段比较。

### P3 CNG 算法句柄每请求重开（crypto.cpp）

`sha256` 每次调用 BCryptOpenAlgorithmProvider→CreateHash→…→Close；
AES-GCM 每次 open + 设 GCM 链模式属性 + GenerateSymmetricKey。
crypto.cpp 头注声称"算法句柄进程内共享"，实现却每次重开——按次开两个
provider + 一次属性设置，纯属浪费。CNG 文档明确：**算法句柄线程安全可共享，
哈希/密钥对象必须按次创建**（后者是安全设计，保留）。

**方案**：进程级缓存 SHA256 与 AES-GCM 两个算法句柄（GCM 链模式只设一次），
哈希/密钥对象仍按次创建销毁。CNG 语义：算法句柄打开后只读、可多线程并发
用于 CreateHash/GenerateSymmetricKey；哈希/密钥对象不可共享（安全设计，保留）。
失败不锁存（审核补入）：仅成功结果进缓存，打开失败当次返回 false、下次调用
重试——与原"每次重开"的逐次语义等价；并发首开用 CAS 收敛，输家关闭自己的句柄。

### P4 vault 初始加载的 restart 抖动（main.cpp composeVaultPage）

`if (!st.vaultLoaded) refreshVault()` 在首个响应到来前**每次 compose 都
cancel+repost** 同一任务（服务线程启动有几百毫秒窗口，期间每次键入/hover
都在重建任务）。`app::async` 的正确用法（EUI-NEO 异步文档）是 in-flight
去重 + 失败退避，而不是每帧 restart。

**方案**（按审核修订）：现有回调无条件 `st.vaultLoaded = true`（失败也置位），
导致退避重试成死代码——改为**成功才置 vaultLoaded，失败只设
`st.vaultRetryAt = now + 400ms`**（PageState 新增字段）。compose 侧守卫：
`!st.vaultLoaded && !running("vault.list") && g_serverState != 2 &&
now >= vaultRetryAt`；监听彻底失败（状态 2）不再重试。手动刷新（存入/删除/
切页后的 refreshVault）保持 restart 语义不变。已核实无"永不重试"死态：
取消路径不执行回调但 running() 已变 false，下次 compose 照常触发。

### P5 Release 编译体积优先（CMakeLists.txt）

Release 用 `/Os`（最小化体积）牺牲速度换瘦身。性能专项应速度优先。

**方案**：`/Os` → `/O2`；保留 /GF;/Gy;/Gw;/Zc:inline 与
/LTCG;/OPT:REF;/OPT:ICF（死代码剥离不受影响，体积增幅预计极小）。

### 明确不做（评估过，收益不足或属框架职责）

- compose 期字符串 id 分配（`"row." + std::to_string(i)`）：框架按 string id
  建树，无法避免；保留层缓存与元素树重建成本由 EUI-NEO Runtime 控制。
- perforation ~44 个虚线 rect：静态子树，框架保留层缓存自动覆盖。
- `recvHeader` 的 find 重扫：32KB 上限下最多 4 次 8KB 重扫，可忽略。
- timer 元素挂载方式：已按需存在（仅反馈窗口期），符合保留层缓存要求。
- httplite.h 客户端：阻塞式按设计，无热路径。
